# RAG 诊断与自动进化系统方案设计 (System Design Architecture)

## 一、 系统概述与定位

本系统是一个旨在为企业级智能知识库（如：对接了 Google Vertex Search 的银行 RAG Flow Engine）提供**非侵入式自动化诊断与提示词自我进化**的独立中枢。

由于现代的 RAG 系统往往受到黑盒检索服务（如 Vertex）表现波动、以及大模型（LLM）天生自带“幻觉编造”、“答非所问”特性的影响，传统通过人工干预去猜测、调试 Retrieval 参数组合和繁复 Prompt 的方式成本极高，且缺乏量化依据。

因此，本系统采用**“观察者模式 (Observer Pattern)” + “评估模型即评委 (LLM-as-a-Judge)” + “编译级提示词优化 (Compiler-based Auto-prompting)”** 三大前沿范式，实现了完全无需侵入原业务代码前提下的：
1. **自动且彻底的“体检诊断”** (量化到底哪里做得差)
2. **E2E（端到端）全切面流水线的自我进化尝试** (通过不断自动调试，将更优的 Prompt 和机制保留并固化)

---

## 二、 核心方法论与设计理念

### 1. 独立观察者架构 (Decoupled Observer)
本功能定位为不干扰主工作流的副产物微服务：
- 您的原系统（如 `agent-kms`）只需做极其低廉的代码改动：即在 RAG 回答结束时，将流水线数据 `{"query", "contexts", "prompt", "answer"}` 落库或投递入消息队列。
- 诊断工具将在独立的物理环境和进程中，异步地拿取离线“标本”（Log档案），进行沉浸式的打分和重跑训练。这就达成了**生产环境零侵入**。

### 2. LLM-as-a-Judge 理念与“银标准”策略
- **无参考答案评估 (Reference-free Eval)**：真实的客服问题往往没有也不可能去全部标定所谓的“标准答案”。系统采用了基于数理逻辑的无感打分，比如判断：**“回答里出现的所有实体、数字概念，都能在这个上下文里找得到吗？”** 如果找不到即判定触发**幻觉 (Faithfulness 打分暴跌)**。
- **银标准 (Silver Standard)**：对于部分必须要比对“检索引擎搜全了没有（Context Recall）”的打分，系统使用了最强的“法官大模型”充当标注员。我们让法官通读高质量档位的参考文档，自动合成出完美的、不带口语累赘的“银标准答案”，然后让我们的系统拿去跟真实测试环境进行对标。

### 3. Pipeline 端到端 (E2E) 优化
我们并非把系统拆成一个个原子再去针对性调整 prompt（那会导致碎片化且互斥的指令堆砌），而是打造一条真正的连缀型全阶流水线 (Pipeline Optimizer)：
- 从将最初提问送进**“检索词重写库 (QueryRewrite)”**开始。
- 到带着优质搜索词返回后，进入**“答案生成库 (Generator)”**。
- 这两个模块同时被纳入综合惩罚分数函数（Multi-objective Metric），这意味着模型任何单方面的“小聪明”（比如编造）只要触发了底本的不一致，统统不及格淘汰！

## 三、 技术架构选择与框架

我们选择了业界极其垂直且代表未来的框架组合 `[ Ragas + DSPy ]` 来落实这一理论。

### 1. 裁判与度量框架：Ragas (RAG Assessment)
**不使用通用的 LangChain 官方评估器的原因：** Ragas 是独家专精于 RAG 各个微观节点的深度评测库它有着极具工业级价值的切割指标。
- **引入的具体指标模块**：
  - `Faithfulness`（生成模块 - 查幻觉）：衡量产物是否有编造的场外信息。
  - `Answer Relevancy`（生成模块 - 查偏题）：衡量生成出来的一大坨话中，多少废话，多少切中痛点。
  - `Context Recall / Precision`（检索模块 - 查底层 Vertex 能力）：检查文档片段里到底有没有捞全需要的信息。

### 2. 进化与编译框架：DSPy (Declarative Sequencing provided by Python)
这可以说是系统的“灵魂（核心）”。我们使用由斯坦福大学打造的 DSPy 框架而非任意一种 AutoGPT 等方案，是因为它的哲学是：**把 Prompt 视为模型的超参数 (Hyperparameter)。**
- DSPy 不是用规则去跟各种 LLM 绕圈子，而是**直接把“编译程序”的想法拉入调优**。
- 我们使用它自带的编译器 `BootstrapFewShot`。我们仅仅喂给它一些有代表性的劣质/优质样本（我们的 Mock 里的 Bad Case），它就能自己当场不断变异自身的话术方式、并在尝试中寻找通过 Ragas 严苛审核后脱颖而出的那一部分，“固化”成为具有极其优质 Few-shot（微调范例）的底层 Prompt 设置文件（JSON 格式快照）。

## 四、 具体模块实现细节解析

项目当前代码落地切分为三大独立脚本层段。

### 第一层：`00_silver_standard_generator.py`
**设计目的：** “无人工标注”困境中的基调定鼎器。
- 加载线上的历史日志，直接把上下文发送给更具推理逻辑的（如 GPT-4o 或 Gemini-1.5-Pro）判官模型。强令它写下“完美参考答案”。
- 输出一份具有 `reference` 字段的数据源，补齐评测短板。

### 第二层：`01_ragas_evaluator.py`
**设计目的：** “找茬”雷达。
- 把前线系统回传的真实的 `query`、`context` 以及当初那个系统返回的可怜 `answer` 一并输入。
- 采用 `evaluate` 全家桶进行矩阵式批量打分，并下沉到 `evaluation_detailed_results.csv`。由此您可以清晰看到每一条长尾问题，它到底死在了 Vertex 搜不出，还是 LLM 在瞎掰。

### 第三层：核心大脑 `02_dspy_optimizer.py`
**设计目的：** 端到端联合惩戒大逃杀，诞生最强版本。
- **双管线模块 (`E2E_RAG_Pipeline`)**：用结构体锁死了“从最初提出问题” -> “变成 Google Vertex 精简入参” -> “吐出最终答案”的必然流程。
- **联合度量打分尺 (`comprehensive_ragas_metric`)**：在这个核心函数中，发生了两个生态的史诗级碰撞！DSPy 本身不具备业务鉴卡的能力，它只是无休止地进行参数寻优组合迭代。此时，它每一次突变的输出，我们都在此函数内构造出一个迷你的 Ragas Dataset 环境，调用 OpenAI/Vertex Embedding 计算并执行基于法官的评分（`0.7 * f + 0.3 * r`）。
- **BootStrapFewShot 淘汰机制**：在这个综合分数达不到超高预期设定门槛前，任何 DSPy 的瞎编都以淘汰告终，直到它逼自己写出极其守规矩、高质量防幻觉且高度相关的生成词条！最终产出一份包含所有优胜变体组合的 JSON 快照设定，您再通过您的 Go/Python 服务层重载这个系统设定。

## 五、 Edge Cases 与前沿处理 (针对 Vertex)
针对您使用的 Google Vertex Search，系统在评估和调优时考虑到了：

1. **混合 Chunking (HTML 与 Markdown 混排的评估)：**
   面对 Vertex 特立独行返回 `<table>` HTML 的现象，这是 Google 聪明地防范丢失二维数据关系的产物。但复杂的 HTML 可能冲散 Token 密度。
   - 这套系统的伟大之处在于：如果在您不去掉 HTML 标签直接开跑的情况下，只要它在 Ragas 的 `Context Recall` 评分高，反而 `Faithfulness` 得分低，这套系统就能明确告诉您该去您主线系统里加一个基于 `BeautifulSoup` 的“去除多余 `<style>`/`<class>` 标签，保留骨干”的前置清洗拦截器。而不是盲目去改 Vertex 的权重。
2. **防范过度 Reranking：**
   通过在全管线监控中，一旦发现部分特定意图词的 `Context Precision` 在 Vertex 打开重排以后呈现负向下降趋势，我们可以利用进化出的大模型设定添加旁路系统：“只要分析出用户具备硬资产单号编码核对的意图，绕开语义引擎重排”。
